## 2. Defects found and fixed in this pass

| # | Flaw | Why it mattered | Fix |
|---|---|---|---|
| F1 | `deploy.yml` allowed `workflow_dispatch` from any branch | A manual run on a feature branch would ship that commit to production. | Deploy job now requires `refs/heads/main`. |
| F2 | `docker-compose.prod.yml` ran `cloudflared:latest` with auto-update disabled | Unpinned, unreproducible edge component; the other compose file already pinned it. | Pinned to the same `CLOUDFLARED_VERSION` default. |
| F3 | The production image was only ever built on the server at deploy time | A broken Dockerfile or base-image bump (e.g. the Node 25 PR) would first fail during a release. | New `image` CI job builds the image and starts the `tsx` runtime. | F7 | README claimed "170+ tests" | Stale (586). | Updated. |

Checked and found **not** to be a flaw: rolling back after a failed deploy re-runs `npm run migrate` on the older commit. The migrator only applies files not yet recorded in `schema_migrations`, so it is a no-op against a newer database and cannot block the rollback.

## 3. Open findings (need an owner decision or evidence — not changed here)

Ordered by exposure.

**Business**

1. **Sector labels defeat their own evidence gate (high).** All 18 sectors have `availability: "available"` as the catalogue *baseline* (`src/platform/catalog.ts`). The per-sector gate can promote a label but, because the baseline is already Available, a missing or lapsed acceptance can never demote it. That includes customs brokerage, cold chain, aviation and dangerous/regulated cargo, which `RELEASE_ACCEPTANCE.md` itself lists as Planned specialist releases, and it conflicts with blueprint §29 ("do not sell all 18 sector packs at launch"). Recommendation: set the baseline to Pilot/Planned per `RELEASE_ACCEPTANCE.md` and let accepted gates promote. This is recorded as an owner decision, so it was left as is.
2. **Allowances and prices are hypotheses that become permanent (high).** Plan versions are immutable and subscriptions keep what they bought (decisions 4, 16, 19, 30). Publishing guessed `trips`, `orders` or `parcels` allowances to paying customers locks them in. Run the ≥5 design-partner pilot before taking payment on versions 2+.
3. **Tax and legal basis is unconfirmed (high).** An India-GST freelancer selling to UAE customers (decision 2), Terms/Privacy/DPA marked Draft (13), coverage copy draft (6). These need a tax adviser and lawyer, not code.
4. **Support promise is undefined (medium).** No published hours or tiers (decision 7). Do not advertise 24/7 on low plans.
5. **Mid-period upgrades are not prorated (medium, decision 12).** Customers upgrading mid-month pay a full first month; expect disputes.

**Operational**

6. **Single server (high).** The lean AWS and Oracle paths run on one VM with no standby. Recovery depends on the backup, so the restore must be rehearsed.
7. **Restore is not scheduled (high).** `npm run restore` and `npm run verify` exist, but nothing runs an isolated restore on a schedule or alerts if it fails. A backup that has never been restored is unproven. Add a weekly restore-and-verify job.
8. **No backup taken before a production migration (medium).** `deploy.sh` migrates and then checks health. Migrations are forward-only, so rolling code back leaves the old code on the new schema. Adopt an expand/contract rule for destructive changes and take a backup first.
9. **R2 backup retention is unmanaged (medium).** Local copies are pruned after 3 days; the bucket grows forever and has no lifecycle rule. Backup credentials sit in a plain 0600 file.
10. **Deploy gate is thinner than CI (medium).** `deploy.yml` runs typecheck and the embedded-database tests only. The real-Postgres and browser jobs live in `ci.yml` and are not required by the deploy.
11. **Provider acceptance is entirely outstanding (high).** Stripe, Razorpay, e-invoicing, WhatsApp, noon, e-AWB, DHL, Google Routes and bank feeds are built and tested against simulators only (`RELEASE_ACCEPTANCE.md`). Nothing should be described to customers as live until each row has sandbox evidence.
12. **Alert delivery is untested (medium).** Prometheus rules validate syntactically; real delivery, acknowledgement and a named incident owner are still open.

**Workflow / documentation**

13. `VALIDATION.md` still reports the 10–11 October counts (220 tests); a dated row for this run has been added.
14. Browser acceptance for Delivery/COD and Fulfilment (`e2e:delivery`, `e2e:fulfilment-delivery`) is missing from the checkout (stated honestly in the README and backlog), so those two money-handling workflows have no browser regression test in CI.

## 4. What "recreate" should mean

Nothing here justified rewriting the application: the tenant isolation, ledger, payment and COD controls are covered by a large passing suite. The sensible rebuild order is the open list above: (1) correct the sector baseline, (2) add the weekly restore drill and pre-migration backup, (3) make deploy depend on the full CI, (4) restore the two missing browser walkthroughs, (5) obtain the provider sandbox evidence, (6) get the legal and tax review, then publish pricing. Items 1 and 2 are the first ones I would take on next if you want them done.
